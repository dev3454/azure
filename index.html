07 · BUSINESS CONTINUITY

What happens when a PC dies?

Azure DevOps protects versions that were pushed. It cannot retrieve changes that existed only on a failed developer disk.

✓Committed AND pushed

Recover by installing Git on another computer and cloning the repository.

Recoverable from Azure Repos
!Not committed or pushed

Only a separate backup of the working folder can recover code saved before the most recent successful backup.

Azure Repos alone cannot recover it
⌨Developer working folderCommitted + uncommitted work
Regular Git push↗
Automatic file backup↘
☁Azure ReposPushed commits
▣Backup server / NASSnapshots of working files
Practical standard: Commit and push small increments during the day. Independently back up active source folders to another device using a properly configured backup tool, e.g. UrBackup, and test a restore. An hourly backup can still lose work created after the last successful snapshot. Protect the backup server too.
08 · TEAM RULES

Recommended engineering standards

Simple consistent rules avoid accidental overwrites, fragile merges, and invisible work.

01

One branch per task

Name branches feature/name/short-task, bugfix/name/issue, or hotfix/name/issue.

02

Protect main

Require PR reviews and checks before merging. Restrict direct changes and bypass permissions.

03

Push frequently

Push work-in-progress commits to your own branch; never push unstable work directly to main.

04

Never commit secrets

Do not track live Web.config passwords, tokens, certificates, or machine-specific credentials.

05

Review before add

Use git status, git diff, and git diff --cached before a commit.

06

Backups are automatic

Version control does not protect uncommitted changes; schedule independent workstation backups.

Suggested daily sequence: fetch/pull your base → create branch → edit → review → stage → commit → push → PR → review → merge → update local branch.
